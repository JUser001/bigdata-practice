# Week 5 · observations

## Task 1
In the broken version (beta = 1, no teleport) a dead end's rank is multiplied by an all-zero column, so it simply leaves the graph and the total drains to 0; I send it to a uniformly random page instead (the surfer stuck at a dead end teleports), which conserves total rank. The same one line repairs the spider trap because teleporting guarantees every page a steady inflow and caps how long the surfer can stay inside any group, so nothing can drain the graph and nothing can hoard rank. `beta` is the probability that the surfer follows a link; with probability `1 - beta` they get "bored" and jump to a page chosen uniformly at random.

## Task 2
As beta goes 0.5 → 0.99 the iteration count on the harness graph grew only from 14 to 24 (tol 1e-10), well below the `ln(tol)/ln(beta)` bound (about 2,300 at 0.99), because the error shrinks by `beta * |lambda_2(M)|` per step and this graph is nearly acyclic; on a slow-mixing graph I built (two communities joined by 3 one-way edges) it grew 24 → 1,463, so the bound is real but only reached by graphs with slow mixing. For A4, growing the graph 16.7× left the iteration count unchanged (20 → 21 at beta 0.85) but the time grew 15–29×: the count depends on beta and mixing, while the time is the cost of one pass over all edges. For A6, the top-10 set never changed and the order was the same for every beta from 0.55 to 0.99; it first changed at 0.54 (two adjacent pages swapped), so on this graph 0.85 is a tuning detail, but adjacent ranks (some 1.8e-3 apart) should not be over-read. Note these timings come from a 1-vCPU cloud sandbox, not my own computer.

## Task 3
Instead of M (n² = 1,440,000 floats) I store each node's list of out-neighbour ids plus its out-degree: E + n numbers (5,877 + 1,200), and hold r and the new r on top, 10,677 numbers in total, about 135× less than the dense version. The teleport term and the dead-end redistribution give *the same amount to every node*, so I compute them once per iteration as one scalar, `((1 - beta) + beta * dead_end_mass) / n`, and start the new vector at that value; only the real edges are then added, so no n × n matrix (or per-node dead-end column) is ever formed. My worst per-node difference from the dense answer is 1.2e-15: it comes from floating-point rounding, since the two versions add the same terms in a different order and the dense one also sums explicit zeros; it is not a bug.
